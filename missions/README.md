# missions/

에이전트에게 주는 「용무」. **정답은 여기 없다.**

| 파일 | 무엇 |
|---|---|
| `public.json` | 준비된 미션 9건. 105회 실측이 전부 여기서 나왔다 |
| `security.json` | 검증용(로컬 허니팟). 통계에 섞이지 않게 **일부러 분리**돼 있다 |
| `keys/` | ⚠️ 정답 키. **`agent/src/judge.ts` 외에서 읽지 않는다** |
| `tasks.json` | **즉석 실행용 용무 후보** ← 2026-08-12 추가 |
| `categories.json` | 용무의 **분야**와 그 분야에서 바로 넣어볼 주소 ← 2026-08-15 추가 |

## `tasks.json` — 화면에서 고르는 「用事」

즉석 실행(`agent/src/live.ts`)은 URL을 그 자리에서 받는다. 그러면 미션이 미리 없으므로
**용무만 고르게 하고 URL과 합쳐서 즉석 미션을 만든다.**

```
받은 URL  +  tasks.json의 한 줄  →  Mission (id: live__<task>__<host>__<시각>)
```

`goal_ja`가 **「このサイトの中で」로 시작하는 이유**: 준비된 미션은 「新宿区の転入届」처럼
사이트 이름이 문장에 박혀 있다. 즉석 미션은 어느 사이트가 올지 모르므로 그렇게 못 쓴다.
사이트 이름을 넣지 않은 채로 「이 사이트 안에서 찾아라」로 범위를 준다.

### `categories.json` — 왜 분야로 나누는가

목록이 평평하면 **은행 주소에 「転入届」를 붙일 수 있다.** 그렇게 돌린 실행은 실패하는데,
그 실패가 사이트 탓인지 조합 탓인지 아무도 구별할 수 없다. 계측이 아니라 사고가 된다.

그래서 화면은 **분야 → 주소 → 사람 → 용무** 순으로 묻는다. 분야를 먼저 고르면
말이 안 되는 조합이 애초에 화면에 나오지 않는다.

```
categories.json  분야 4종 + 그 분야의 대표 주소
tasks.json       용무 + 그 용무가 나오는 분야(`categories: [...]`)
```

- `categories`가 **빈 배열**인 용무는 화면에 안 나온다. 지운 게 아니라 **주소로는 여전히 돈다** —
  `/live?task=denki&...`로 남아 있는 옛 실행을 그대로 다시 돌릴 수 있어야 하기 때문이다
- `denki`(東京電力)가 지금 빈 배열인 이유: 실측에서 **봇 검사 화면**(「セキュリティ検証の
  しばらくお待ちください」)에 걸렸다. 대조군조차 통과하지 못한다 → 그 자리에서 권하지 않는다
- 대표 주소는 전부 `npm run preflight -- <url>`을 통과한 것만 싣는다.
  ⚠️ 東京大学(`www.u-tokyo.ac.jp`)은 preflight에서 접속 자체가 안 돼서 뺐다

### `max_steps` — 왜 용무마다 다른가

`public.json`은 처음부터 **자치체 9건은 20수, 은행·전력·대학 6건은 30수**였다.
사이트가 깊기 때문이다. 그런데 즉석 실행만 전부 20수로 굳어 있었다.

그래서 실측에서 이런 일이 났다 — **대조군이 목적지 한 칸 앞에서 잘렸다.**

| 실행 | 20수째에 있던 곳 | 판정 |
|---|---|---|
| 慶應義塾大学 · 학비 · 대조군 | `/ja/admissions/fee/faculty/` (연도별 링크까지) | 미도달 |
| 青山学院大学 · 학비 · 대조군 | `/life/expenses/` (**학비 페이지 그 자체**) | 미도달 |

이건 사이트가 어려운 것도 제약 탓도 아니고 **우리가 센 칸이 모자란 것**이다.
화면에는 「이 사이트가 어렵다」가 아니라 **「이 도구가 못 한다」**로 보인다. 그건 계측이 아니다.

→ 용무에 `max_steps`를 적는다. 없으면 20. 은행·통신·대학·문의처는 30 —
  **`public.json`이 같은 도메인에 이미 주던 값과 같다.** 새 규칙이 아니라 흘리고 있던 규칙이다.

⚠️ **이걸로 제약측이 유리해지지는 않는다.** 사람쪽 프로필은 자기 인내치가 먼저 걸린다
(`smartphone-novice` 12클릭 / `busy-worker` 8클릭 / `senior-70s` 15클릭 / `resident-n3` 20클릭).
30수가 실제로 풀어주는 것은 **대조군(30클릭)과 `senior-70s-patient`(30클릭)뿐**이다.
즉 이 변경은 **대조군을 더 잘하게** 만든다 — 우리 주장에 불리한 방향이다.

우선순위는 `--max-steps` > 용무의 `max_steps` > 20. 손으로 준 값이 이겨야 검증용으로 짧게 돌린다.

### ⚠️ 정답 키가 없다

`keys/`에는 이 조합의 정답이 없다. 있을 수가 없다 — 어느 사이트가 올지 모르기 때문이다.
그래서 즉석 실행의 도달 판정은 **AI 하나뿐**이 된다 (준비된 미션은 사람이 만든 키 + AI의 2단 판정).

이 사실은 숨기지 않고 세 곳에 남는다:

1. `Judgement.key_available` — 판정 결과 안
2. `Verdict.reason_ja` 끝의 「※ このURLには人が用意した正解キーがないため…」
3. 진행 상황(`Progress.start.key_available`) → 화면

**즉석 실행 결과를 105회 실측과 같은 급으로 말하지 않는다** (절대규칙 4).

### 결과가 저장되는 곳

즉석 실행은 `agent/runs/`가 아니라 **`agent/live/`**에 쓴다.
`scripts/build-web-data.ts`가 `agent/runs/` 전체를 훑어 화면의 모든 숫자를 만들기 때문이다.
같은 폴더에 두면 심사장에서 넣은 URL이 105회 통계에 섞인다.
