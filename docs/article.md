# サイトを「使いこなせない」AIを作ったら、いちばん最初に見つかったのは自分たちのバグだった

> AI HACK 2026 応募作品 **ツマヅキ / Tsumazuki** の開発記です。
> LLM 呼び出しはすべて [OrcaRouter](https://www.orcarouter.ai/) 経由で行っています。

## 作ったもの

URL を入れると、それぞれ違う制約を持った AI 利用者がそのサイトを実際に操作し、
**どこで手が止まったか**を記録して返します。

```
URL → 制約プロファイル5種 × 実行 → 各エージェントが止まった地点 → 修正案つきレポート
```

ユーザーテストは本来「正しく作れているか」ではなく「**使えなかった人がどこで諦めたか**」を
知るためのものです。けれど対象者を集めて日程を組んで謝礼を払うと、1 回に数週間かかる。
だから多くのサイトは、リリース後に問い合わせが来るまで気づきません。

その 1 回目を数分で回す、というのが狙いです。

---

## 出発点：既存のエージェントは「うますぎる」

Browser Use をはじめとする既存のブラウザエージェントは、サイトを **使いこなす** ために
作られています。リンクの文言が分かりにくくても、文字が小さくても、DOM を読んで
正解にたどり着いてしまう。

つまり **使いにくさの測定には使えない**。優秀すぎる被験者は、被験者になりません。

だからツマヅキは逆を作りました。**サイトを使いこなせないエージェント**です。

### そして、それをプロンプトでやってはいけない

最初に否定した案がこれです。

```
あなたは 72 歳です。カタカナ語が苦手なふりをしてください。
```

これは動きません。モデルは「アクセシビリティ」の意味を**知ったまま**、
知らないふりを**演じる**だけだからです。演技は漏れます。しかも漏れたかどうかを
こちらから検証できない。

もっと根本的な問題として、知識ベースやプロンプトは能力を **足す** ことはできても、
**引く** ことはできません。「知らない」を後付けで作れないのです。

### 引き算は観測層でやる

そこで、制約を**プロンプトではなく観測層で**適用しました。

```
ブラウザ → observe() → shield() → constrain() → LLM
                                      ↑
                        ここで語彙を伏せる・視界を狭める・道具を取り上げる
                        LLM は「隠された後」の画面しか見たことがない
```

`constrain()` を通らないバイトは LLM に届きません。演技する余地が構造的に存在しない。
これがこのプロダクトの中心で、他は全部その周辺です。

実際に何が起きるか（新宿区トップページ・文字サイズ 200%・高齢者制約プロファイル v1.0）：

| | 制約前 | 制約後（エージェントが見たもの） |
|---|---|---|
| リンク | ウェブアクセシビリティ方針 | ウェブ◯◯◯◯◯◯◯◯方針 |
| リンク | サイトマップ | ◯◯◯マップ |
| 画面内の要素数 | 270 | 9 |

伏せる根拠は[国立国語研究所「外来語」言い換え提案／外来語定着度調査](https://mmsrv.ninjal.ac.jp/gairaigo_yoron/)です。
「アクセシビリティ」の 60 歳以上の理解率は 2.1%。**私たちが決めた数字ではありません。**
伏せた語には必ず出典と数値が付きます（`evidence()`）。根拠のないマスキングはバグ扱いです。

そして誤差の方向を最初から片側に倒しました。調査に載っていない語は**通します**
（`unknown: "keep"`）。つまり常に **過少マスキング**。
「これは過小評価です」と言えることが防御線になります。

### ついでに刺さった話

このデータで最初に殴られたのは、測った相手ではなく**自分たちの紹介文**でした。
「ウェブサイト」も「サイト」も、伏せる側に入ります。

| 語 | 60 歳以上の理解率 | 全体 |
|---|---|---|
| **ホームページ** | **62.6%** | 82.6% |
| サイト | 7.8% | 34.4% |
| **ウェブサイト** | **4.3%** | 21.5% |

同じものを指す 3 つの言い方で、60 歳以上の理解率が **58 ポイント**違います。
（調査は 2002–2003 年・n=750〜2115。この数字自体の古さは後述します）

「ホームページ」は業界では古い言い方とされがちですが、
**伝わる相手の数でいえば桁が違います。** 私たちのランディングページも、
この時点で書き直す候補になりました。

これがこのプロダクトの一番小さい実例です。**難しくしているのは中身ではなく、呼び方**のことがある。

## 本題：計測器を作るとき、いちばん怖いのは計測器自身のバグ

ここからが、今回いちばん学びになった話です。

5 自治体 × 5 プロファイルで 105 回まわして、こういう表が出ました。

| | 到達率 |
|---|---|
| 対照群（制約なし） | 100% |
| 制約側 | 37〜74% |

さらに面白いことに、**同じ制約なのにサイトによって離脱率が 0% と 94% に割れました**。
違うのはサイトだけ。これは「AI ができない」のではなく **サイトを測った値** である証拠で、
同時に「どんなサイトでも悪く出る装置ではない」証拠でもあります。

いい数字が出た、と思いました。

**この表の数字は、このあと全部捨てます。** 先にそう書いておきます。

### ところが

多言語対応を測ろうとして、外国人住民プロファイルに「英語ページを探す」条件を足したときです。
新宿区で英語ページに到達できない。ログを見たら、こう出ていました。

```
guard: 외부 사이트 (www.foreign.city.shinjuku.lg.jp)
```

> 内部ログとコードコメントは韓国語です（チームの作業言語）。読みにくくてすみません。
> ただ、この記事に貼るログは**リポジトリを `grep` して同じ文字列が出てくるもの**にしています。
> 訳した文を貼ると、確かめようとした人が見つけられません。

新宿区の外国人向けページは、**別サブドメイン**にありました。
そしてエージェントの遷移ガードは origin 完全一致だった。つまり **こちらが塞いでいた**。

これは単なるバグではありません。**測定値の意味が変わります。**
「英語では到達できなかった」は、サイトの問題ではなく私たちの道具の問題でした。

慌てて当時の旧世代トレース 160 件を全部洗いました。「外部サイト」として弾いたものが 9 件 8 ラン。
**そのうち 5 件は同一自治体内**でした（新宿区の外国人向け・FAQ、渋谷区、港区の多言語通訳）。

### さらに、もっと大きいのが出てきた

ついでに `guard:` で始まるログを全部数えたら、一桁ひどいものが出てきました。

```
guard: 허용되지 않는 스킴 (javascript:)
```

ブラウザの**外**にあるアプリを開くだけで、ページ上では何も起きないものは
押させないようにしていました。`mailto:` `tel:` — そこに `javascript:` も入れていたのです。

でも `javascript:` は「行き先」ではなく「**やること**」でした。
`javascript:void(0)` を href に持つリンクは、外に出て行くどころかそのページのボタンです。

実測を数えると、こうでした。

| サイト | `javascript:` 遮断 |
|---|---|
| 港区 | **78 回 / 22 ラン** |
| 大泉町 | 31 回 / 13 ラン |
| 浜松市 | 3 回 / 1 ラン |

そして弾かれていたのは「検索」45 回・「メニュー」33 回・「チャットで相談！」31 回。
つまり**モバイル表示のハンバーガーメニューと検索ボタン**です。

港区の到達率を、この遮断が起きたランと起きなかったランで割ってみました
（どちらも**直す前のコード**のランだけで比べています。直したあとのランを
「弾かれなかった」側に混ぜると、差が実際より大きく出ます）。

| | 到達率 |
|---|---|
| `javascript:` が弾かれたラン | 2/22 = **9%** |
| 弾かれなかったラン | 8/14 = **57%** |

**「港区は離脱率 94%」という、いちばん強い数字の正体がこれでした。**
サイトが難しいのではなく、私たちがメニューボタンを押させていなかった。

### 直したら結果が変わった

修正後、港区・同条件で回し直すと、2 ラン目は**初手で「メニュー」を押して**
14 ステップで到達しました。ガード遮断は 12 回 → **0 回**。

そして、ここで一番大事な判断をしました。**105 回を全部捨てて、測り直す。**

片方だけ直して並べたら、「渋谷区 0% ↔ 港区 94%」という比較自体が無効になります。
同じコードから出た数字でなければ、サイト同士を比べる資格がない。
新しい世代は `batchv2__` に分けて貯め、古い方は**消さずに残しました** —
直す前と後の差そのものが根拠だからです。

```
再測定：7プロファイル × 4回 × 5自治体（同じ用事＝転入届）
うち公表集計に入れるのは5プロファイル。残り2つは実験用（version が -exp）で、
集計スクリプトが自動で外します
```

結果は後で出しますが、その前に**測り直しの最中にさらに二つ出た**話をさせてください。
数字はそれを直したあとのものです。

### 測り直している最中に、さらに二つ出た

測り直しの途中で OrcaRouter の残高が尽きました。ところがバッチは止まらずに回り続け、
残りは全部 `outcome: "error"` として保存されました。

問題はその先です。集計は `error` を **離脱として数えていました。**
`error` は `reached: false` だからです。

手元に保存してあるトレース **367 件**（捨てた旧世代も含む全部）を開いて、
error になっていた **35 件**の理由を一件ずつ数えました。

| 理由 | 件数 |
|---|---|
| OrcaRouter 残高切れ | 20 |
| ミッションに正解キーがない（旧世代のみ） | 8 |
| 画像入力の未対応（画面テキストを読まないプロファイル） | 6 |
| ブラウザが閉じた | 1 |

**サイトのせいで失敗したものは一件もありませんでした。** 全部こちら側の事情です。
これを離脱に数えるのは、破れて届いた宅配便を「顧客が返品した」と数えるのと同じです。

このうち、公表する集計（`batchv2` 世代・公表 5 プロファイル）に入っていたのは **18 件**です。
集計から外し、**外した件数を必ず画面に出す**ようにしました。隠せば質疑で崩れます。
誤差の向きも確かめました — 外すと離脱率は**下がる**。過小側です。

もう一つは、もっと地味で、もっと危ないものでした。

バッチが途中で二度死んだので、足りない分だけを継ぎ足していました。そのとき
「実行回の番号は繰り返し回数ではなく**条件**だ。欠けた番号を正確に埋めないと、
自治体ごとにクリック予算と流入経路が変わってしまう」と考えました。
プロファイルの JSON に、はっきりそう書いてあったからです。

```json
"variants": [
  { "suffix": "a", "patience": { "clicks": 12 }, "entry": "top" },
  { "suffix": "b", "patience": { "clicks": 18 }, "entry": "search_referral" }
]
```

念のためコードを追いました。**一度も読まれていませんでした。**

`variants` から取り出しているのは `suffix` と言語希望の二つだけで、`patience` は
プロファイル直下の値しか読んでいません。そして `suffix` は、取り出したあと使う場所がない。

つまり 1 回目と 2 回目は、条件の違う二人ではなく、**同じ条件の二回**でした。
設定ファイルの中で、生きているように見えて死んでいたのです。

計測データそのものに被害はありませんでした。どの番号を埋めても同じ条件だからです。
崩れたのは、私たちが自分の仕組みについて持っていた**説明**の方でした。
この記事の下書きにも、いったんは「1 回目は 12 クリック、2 回目は検索から流入」と
書いてしまっています。JSON を読んで、コードを読まずに。

同じ理由で、「実行ごとのばらつきは設計で作っている」という説明も取り下げます。
ばらつきは設計ではなく、**モデルの出力のゆらぎ**から出ていたものでした。

欠けた番号を埋める口（`--variant-list`）は、結局そのまま足しました。
ただし目的は条件を守ることではありません。**どのマスが何回回ったかを、
ディレクトリを開かずにファイル名で数えられる**ようにするためです。

### 学び

計測器を作っているとき、バグは「動かない」という形では出てきません。
**それらしい数字**という形で出てきます。しかも最初のバグは、私たちにとって
**都合のいい方向**に効いていました。94% という派手な数字をくれていたからです。

共通していたのは、**どれもエラーを出さなかった**ことです。
遮断は仕様どおりに動き、残高切れはきちんと記録され、設定ファイルは正しい JSON でした。
壊れていたのは動作ではなく、**出てきた数字の意味**と、**自分たちの説明**の方でした。

だから「テストが通るか」では見つかりません。トレースを一件ずつ開いて数え、
設定ファイルに書いてある値が**本当に読まれているのか**をコードで追うしかない。

そして四つ目（このあと書きます）で、もう一つ学びました。
**ログが出ていても足りない。** あれは黙って落ちたのではなく、
`외부 사이트` とはっきり記録していました。それでも見落としたのは、
**その文言が原因を言い当てていなかった**からです。本当の理由は `http` と `https` の違いでした。
ログは「何が起きたか」ではなく「**なぜ起きたか**」を書かないと、あとで自分が読み違えます。

だから今は、遮断まわりを主張の範囲そのものとして扱っています。
「何を止めて何を通すか」の表をテストで固定しました（`agent/test/host-guard.test.ts`・韓国語です）。

```ts
test("★ 실측으로 막혔던 자치체 서브도메인이 이제 통과한다", ...)
test("★ 자치체를 넘어가면 막힌다 — 여기가 넓어지면 계측이 무효가 된다", ...)
test("전자신청 SaaS는 서브도메인을 열어도 계속 막힌다 (절대규칙 5)", ...)
test("★ 같은 자치체 안이면 http↔https는 통과한다 — 여기가 막히면 英語ページの入口が閉じる", ...)
```

書いてみて気づいたのは、**止まるべきものが止まるテストの方が数が多い**ことです。
開けすぎるミスは目立たない。`tokyo.jp` まで登った瞬間に東京都全域が開いて、
「このサイトを測った」という文が成立しなくなります。

## 測り直した結果

**125 ラン / 5 自治体 / 同じ用事（転入届）。** 全部、直したあとの同じコードから出ています。

計測できなかった 18 ラン（残高切れ・画面イメージ入力の未対応）は集計から外し、
**外した件数を画面に出しています。** 理由を一件ずつ見ましたが、
サイトのせいで落ちたものは 0 件でした。

### プロファイル別

| プロファイル | 到達 | 到達率 |
|---|---|---|
| 対照群（制約なし） | 21/23 | **91%** |
| busy-worker v1.0（忍耐予算 8 クリック / 2 分） | 17/27 | 63% |
| resident-n3 v1.3（行政漢語 134 語を伏せる） | 14/26 | 54% |
| senior-70s v1.0（外来語マスク＋表示 200%） | 13/24 | 54% |
| smartphone-novice v1.0（※下記） | 10/25 | 40% |

`resident-n3` の 134 語は[出入国在留管理庁・文化庁「やさしい日本語」書き換え例](https://www.bunka.go.jp/seisaku/kokugo_nihongo/kyoiku/92484001.html)（2020-08）の
**指定リスト**です。理解率を測った調査ではないので、この語には %（理解率）を付けません。
外来語のほうだけが理解率つきです。

### 自治体別 — ここがこの企画の主張です

**同じ用事、同じ制約、同じモデル選択ルール。違うのはサイトだけ**です。

| 自治体 | 対照群 | 制約側 |
|---|---|---|
| 渋谷区 | 4/6 | **23/24 = 96%** |
| 群馬県大泉町 | 5/5 | 15/22 = 68% |
| 浜松市 | 4/4 | 9/19 = 47% |
| 新宿区 | 4/4 | 6/17 = 35% |
| 港区 | 4/4 | **1/20 = 5%** |

港区を見てください。**制約なしなら 4 回中 4 回とも終わります。**
通れない場所ではないのです。それでも制約側は 20 回のうち 1 回しか着かない。

これが「AI ができない」のではなく **サイトを測った値**だ、と言える理由です。
どんなサイトでも悪く出る装置なら、渋谷区の 96% は出てきません。

### 先に言っておく弱点が三つあります

**① 対照群は 100% ではありません（21/23）。**
落ちた 2 件はどちらも渋谷区で、**同じページ**（`/contents/shinsei/jumin/`）で手が尽きました。
ただし判定文は 2 件で違います。

> 現在表示されているのは「転居届（渋谷区内の引っ越し）」のページであり、
> 利用者が知りたい「転入届」ではありません

> 現在のページは「申請・各種申し込み一覧」であり、「転入届（区外から渋谷区へ）」の
> 手続き種類が列挙されているのみで、具体的な持ち物などの詳細情報は掲載されていません

1 件目は**転居**届と**転入**届の取り違えです。一文字違いで意味が違うページが並んでいます。
2 件目は取り違えではなく、一覧までは着いたのに**その先に持ち物が無かった**方です。
どちらも制約なしのエージェントが 20 手を使い切って辿り着けませんでした。
これは私たちのバグではなく、サイトの実際の落とし穴だと思っています。

（残り 6 件は OrcaRouter の残高切れで `error` になったもので、分母の 23 から外しています。
この扱いは全プロファイル共通です。）

**② 渋谷区だけ、制約側（96%）が対照群（67%）を上回っています。**
対照群の n が 6 と小さく、上の 2 件がそこに乗っているためです。

**③ smartphone-novice は、設計どおりに動いていません。**
「画面の見た目だけで判断する」プロファイルのはずが、画像入力が未対応のため、
実際には**本文なし・リンク名だけ**で動いています。40% はプロファイルどおりの結果ではない。
画面にもこの注記をそのまま出しています。

そして 25 マスのうち **9 マス（36%）** は、同じ条件で ○× が揺れました。
**マス単位では断定しません。**プロファイル軸とサイト軸までにとどめます。

### 「それ、制約のせいですか？ 画面が狭いだけでは？」

制約プロファイルのうち 3 つは画面幅 375px です。だからこの質問は必ず来ます。

答えを用意してあります。**対照群を 375px にしただけのもの**を、同じバッチで一緒に回しました。
違いは画面幅ひとつだけ。語彙マスクなし、道具の制限なし、予算も同じです。

| | 到達率 |
|---|---|
| 対照群（PC 幅） | 91% |
| **対照群を 375px にしただけ** | **85%** |
| 制約側でいちばん高いプロファイル | 63% |

**幅だけなら 6 ポイントしか落ちません。** 制約側はそこからさらに 22 ポイント落ちる。
「狭いから」では説明がつかない、と言えます。

しかもこの 85% と 63% は、**きれいに 1 対 1 で比べられます。**
「時間がない人」プロファイルは、幅も語彙も道具も 375px の対照群と**完全に同じ設定**で、
違うのは**忍耐予算だけ**だからです（30 クリック / 15 分 → 8 クリック / 2 分）。

```
対照群（375px）   幅375px・語彙制限なし・道具制限なし・30クリック/15分  → 85%
時間がない人      幅375px・語彙制限なし・道具制限なし・ 8クリック/ 2分  → 63%
                                                       ↑ ここだけ違う
```

なお、幅が効いたサイトは 5 つのうち 1 つ（新宿区 4/4 → 2/5）だけでした。

**ただし全部のプロファイルにこの相手がいるわけではありません。**
高齢者プロファイルは表示 200%（実効 640px）、スマホ初心者は実効 250px です。
この 2 つには幅の基準線がまだないので、落ち幅のうちどれだけが幅のせいかは**言いません。**

### 「英語で済ませたい」を一行足すと、サイトによって逆を向く

もう一つ、同じバッチで回した実験があります。日本語語彙の制約に、
**用事の一行だけ**を足したものです — 英語で済ませたい。

| 自治体 | 日本語のまま | ＋英語で済ませたい |
|---|---|---|
| **群馬県大泉町** | 4/5 | **6/6** ↑ |
| 港区 | 0/5 | 1/5 ↑ |
| 浜松市 | 1/5 | 1/5 → |
| ~~新宿区~~ | ~~3/5~~ | ~~1/5~~ **← 取り下げ（下記）** |
| **渋谷区** | **6/6** | **3/6** ↓ |

上がったのは群馬県大泉町です。外国人住民の割合が高いことで知られる自治体で、
実際に多言語の案内が用意されています。逆に渋谷区は、日本語なら 6/6 だったものが半分になる。

### そして、この記事を書きながら四つ目が出ました

新宿区の行だけ取り下げています。理由を書きます。

**この記事の推敲中に、貼ったログを `grep` で確かめようとして、四つ目のバグを見つけました。**
最初のバグ（サブドメイン遮断）を直したはずの新しいバッチで、**同じ遮断がまだ 9 件残っていた**のです。

```
guard: 외부 사이트 (www.foreign.city.shinjuku.lg.jp)
```

直したのはホスト名の判定だけで、**プロトコルは完全一致のままにしてありました。**
そして新宿区は、自分のサイトの中で外国人向けページへのリンクをこう張っています
（トレースに残っていた実際の遷移先です）。

```
http://www.foreign.city.shinjuku.lg.jp/en/
```

`https` ではなく `http`。同じ自治体なのに「格下げは許さない」で弾かれ、
ログには**「外部サイト」と書かれていた**。原因を読み違える書き方をしていたわけです。

影響の範囲は数えました。

| | |
|---|---|
| 自分のガードに引っかかったラン | **3 ラン**（すべて英語版プロファイル・新宿区） |
| そのうち**公表している 125 ラン**に入っているもの | **0 ラン** |

公表数字は無事でした。壊れていたのは、いま読んでもらっているこの実験の方です。
なので**新宿区の行は取り下げ**、残り 4 自治体だけで読みます。

| | 日本語のまま | ＋英語で済ませたい |
|---|---|---|
| 5 自治体（新宿区を含む） | 14/26 = 54% | 12/27 = 44% |
| **4 自治体（新宿区を除く）** | **11/21 = 52%** | **11/22 = 50%** |

**下がり幅は 10 ポイントから 2 ポイントになります。** つまり「英語を足すと全体として落ちる」は、
取り下げた行にかなり支えられていました。ここは正直に引っ込めます。

残るのは**方向が割れること**の方です。大泉町は上がり、渋谷区は半分になる。
こちらは自分たちのガードとは関係のないところで起きています。

ガードは直しました（`agent/src/act.ts`／テストで固定）。ただし
**取り下げたランは測り直していません。** 締め切りまでに直したコードで回し直せた分だけを
数字にする、という線を守った結果です。

**ここで止めます。** 1 マス 5〜6 回で、しかも同じ条件でも 36% は揺れます。
「大泉町は多言語対応が優れている」とは**言いません。** 言えるのは
**「同じ用事に言語の希望を一行足すと、サイトによって逆を向く」**までです。

> この 2 つは実験用プロファイル（`version` が `-exp`）なので、
> 上の 125 ランの集計には**入っていません。**集計スクリプトが自動で外します。
> 同じバッチ・同じコードで回したので、並べて読むことだけができます。

## OrcaRouter：装飾ではなく成立条件

1 回の実行は「画面を読む → 次の手を決める」をステップごとに繰り返します。
1 サイトに 5 プロファイル × 複数回を流すと、LLM 呼び出しは数百回。
全部をフロンティアモデルで回すと **1 レポートの原価がサブスク価格を超えます。**

なので [OrcaRouter](https://www.orcarouter.ai/) を使い、ルーティングの入力を
**ステップ種別ひとつ**に絞りました。

| ステップ種別 | 何をするか | 必要な賢さ |
|---|---|---|
| `perceive` | 今どんな画面かを要約する | 定型処理 |
| `decide` | 次にどれを押すか | 選択肢が有限 |
| `judge` | ゴールに着いたか | 誤判定のコストが高い |
| `diagnose` | なぜ失敗したか・何を直すか | レポート本文 |

エージェント側はモデル名を知りません。ルーター側はミッションを知りません。
この分離があるので、**どの原価がどのステップで発生したか**を後から説明できます。

原価は 1 呼び出しごとに記録します。API が原価を返したら `cost_source: "api"`、
こちらが価格表で計算したら `"table"` と区別する。**推定値を実測と呼ばない**ためです。

上の 125 ラン全部で、こうなりました。

| | 金額 |
|---|---|
| 実際に払った額（125 ラン） | **$4.23** |
| 全部を最上位モデル（`anthropic/claude-opus-5`）で回した場合 | $39.98 |
| 差 | **89.4% 減** |

1 ラン **約 3.4 セント**。5 プロファイル分を 1 レポートとしても、数十セントの世界です。

ただし比較の右側は**計算値**です。「ルーティングしなかったら全部これだった」と仮定して、
価格表から出しています。実際にその全量を回して測ったわけではありません。
`cost_source` を分けているのは、この二つを混ぜないためです。

### 原価の穴も書いておく

自慢だけ書くのはフェアではないので、分かっている穴も出します。

- リトライで捨てた 9 回は課金されているはずなのに、記録前に捨てたので金額が分からない
- 診断ステップの原価が長らく 0 で計上されていた。原因は、原価を集める購読を
  ブラウザを閉じるときに切っていて、**診断はその後に走っていた**こと。今は直っています。
  ただし修正日より前に保存したトレースの金額には診断分が入っていません

どちらも**こちらに有利な方向の誤差**なので、聞かれる前に書きます。

## セキュリティ：外部サイトのテキストを LLM に読ませる、という前提

このプロダクトは、信頼できない外部サイトのテキストを LLM に読ませて、
その結果でブラウザを操作させます。プロンプトインジェクションは想定上の脅威ではなく
**業務上の前提条件**です。

観測パイプラインを自前で持っているので、LLM に渡る前に検査できます。

```
ページ → observe() → 【 shield() 】 → constrain() → LLM
                          ↑ ここを通らないバイトは LLM に届かない
```

検証用のハニーポットは**ローカルのフィクスチャにのみ**設置します。
架空の「ツマヅキ市」を作りました。他者のサイトには一切置きません。

ここでも誤差の方向を決めています。**検出は広く、遮断は狭く。**

正常な文を消してしまうと、その後の失敗が「サイトが難しいから」なのか
「こちらが消したから」なのか区別できなくなり、その瞬間に計測値が全部無効になります。
テスト 19 件のうち**半分が誤検知テスト**なのはそのためです。

主張すること：「表にある形は **LLM に届く前に消える**」「モデルはその文字を見たことがない」
主張しないこと：「AI が指示を見破った」「プロンプトインジェクションを防げる」

---

## 主張すること / しないこと

| しない主張 | する主張 |
|---|---|
| 72 歳のユーザーを再現した | 60 歳以上の理解率 30% 未満の語を伏せた状態でタスクが失敗した |
| 実際の高齢者はこう行動する | このプロファイル v1.0 の実行結果である |
| この数字が母集団を代表する | n=125 の制約プロファイル実行結果である |

レポートの数字には**必ずプロファイル ID とバージョン**が付きます。分離した瞬間に
検証不可能な主張になるからです。

### 語彙データの限界（先に書いておきます）

前半で使った理解率には、**二つの弱点**があります。

**① 古い。** 調査は 2002–2004 年です。「ダウンロード」の 60 歳以上 8.2% は、
2026 年の 60 歳以上には当てはまらないでしょう。

**② コホートがずれている。** もっと大きいのはこちらです。2003 年に 60 歳だった人は、
いま 80 代を超えています。**同じ「60 歳以上」でも中身が別の世代**です。
2003 年の 60 歳以上はインターネットに触れずに働き終えた世代で、
いまの 60 代は現役でパソコンを使っていた世代です。

つまりこのデータは、**いまの高齢者より厳しい側に寄っている**可能性が高い。
それでもこの調査を使っているのは、**60 歳以上を分けて数字を出している公的調査が
他に見つからなかった**からです。見つかったら差し替えます。

だから私たちが言えるのは「実際の高齢者がこうなる」ではなく、
**「この語彙表を使ったプロファイル v1.0 ではこうなった」**までです。

### そのほかの弱点

25 マス中 9 マス（36%）は、同じ条件で ○× が揺れました。マス単位で断定はできません。
`resident-n3` の 134 語は理解率ではなく**指定リスト**なので、%（理解率）を付けません。
`smartphone-novice` は設計どおりに動いていません（画像入力が未対応）。

## 技術構成

- Node 25（`.ts` をそのまま実行。ビルドステップなし）
- Playwright + **システムインストール版 Chrome**
  （バンドルの chromium は指紋が違って WAF に引っかかりやすい）
- LLM 呼び出しはすべて OrcaRouter 経由
- Next.js（レポート画面・その場実行画面）

対象サイトへの姿勢も決めごとにしています。**読み取りのみ。**
会員登録・マイナンバー認証・フォーム送信・ログイン・電子申請システムには入りません。
同一ドメインへの同時実行は 1、リクエスト間隔は 4 秒以上、robots.txt に従います。
